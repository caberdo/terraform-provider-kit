# Contributing

Thank you for considering contributing to the Terraform Provider for {{PRODUCT}}! This document
explains how to build the provider, run its tests and get a change merged. Repository conventions
that are specific to the codebase are in [`AGENTS.md`](AGENTS.md); the roles and decision process
are in [`GOVERNANCE.md`](GOVERNANCE.md).

## Getting started

### Prerequisites

* [Go](https://go.dev/doc/install) 1.27.4 or later (the version in `go.mod`)
* [Docker](https://docs.docker.com/get-docker/) with the `compose` plugin, **or**
  [Podman](https://podman.io) with `podman-compose` — only needed for the acceptance suite
* [Terraform](https://developer.hashicorp.com/terraform/install) 1.0 or later — only needed for the
  acceptance suite
* [Git](https://git-scm.com)

### First time setup

```bash
git clone https://{{MODULE}}.git
cd terraform-provider-{{PROVIDER}}
go mod download
make test          # unit tests; the TestAcc* suite skips itself without TF_ACC
```

## Development

### Building

```bash
make build         # ./bin/terraform-provider-{{PROVIDER}}
make install       # install into ~/.terraform.d/plugins for local dev_overrides
```

Add to `~/.terraformrc`:

```hcl
provider_installation {
  dev_overrides {
    "{{REGISTRY_NAMESPACE}}/{{PROVIDER}}" = "/path/to/terraform-provider-{{PROVIDER}}/bin"
  }
}
```

### Project structure

```
main.go                     # provider entry point
internal/                   # provider schema, resources, data sources and client code
examples/                   # example Terraform configurations — the documentation source
docs/                       # generated by `make generate` — never hand-edit
templates/                  # tfplugindocs templates used by `make generate`
scripts/                    # provider-specific helper scripts, if any
.github/                    # workflows and CI-owned configuration
```

See [`ARCHITECTURE.md`](ARCHITECTURE.md) for what the pieces do at runtime.

### Coding standards

* `make fmt` (`gofmt`) and `make vet` (`go vet ./...`) before every commit.
* `make lint` runs golangci-lint with the repository configuration
  ([`.golangci.yml`](.golangci.yml)); CI runs the same config with a pinned linter version, so a
  green local run means a green CI run.
* Follow idiomatic Go and the conventions in [`AGENTS.md`](AGENTS.md): append diagnostics then bail
  out on error, human-readable error titles with a contextual detail, `tflog` at CRUD boundaries,
  and every schema attribute carries a `Description`.
* All resources implement `ResourceWithImportState`; sensitive fields are `Sensitive: true`; an
  attribute that cannot change in place carries `RequiresReplace()`; computed attributes are set on
  every path or carry `UseStateForUnknown()`.

### Adding a new resource or data source

1. Add the client method the {{PRODUCT}} API needs to the provider's client package.
2. Implement the resource or data source with the Plugin Framework, including
   `ResourceWithImportState` for a resource.
3. Register it from the provider's `Resources()` or `DataSources()` method.
4. Describe every schema attribute, mark sensitive fields, validate enums with
   `stringvalidator.OneOf`.
5. Unit tests for the schema and metadata (no server needed) and acceptance tests named
   `TestAcc<Name>…` for the server-facing behaviour.
6. Add the example under `examples/` and run `make generate` so `docs/` is regenerated — `docs/` is
   generated output and is diffed in CI.
7. `make validate-examples` to check the example against the schema.

### Changing an existing resource

Terraform type and attribute names are public API: renaming or removing one breaks user state, so it
does not happen outside a major version. A new attribute is optional (or computed) and documented;
an incompatible change needs `RequiresReplace()` and a `BREAKING CHANGES` entry in
[`CHANGELOG.md`](CHANGELOG.md).

Cite the server behaviour you are encoding (route, status code, payload) in the pull request
description. A route that exists in the documentation is not proof that a capability works; the
provider's tests should show the behaviour against a real server or a faithful mock.

## Testing

### Testing policy

* **Major new functionality MUST come with tests in an automated suite.** Resource and data source
  behaviour is asserted with acceptance tests against a real {{PRODUCT}} server; parsing, mapping
  and helper logic is asserted with unit tests.
* **Bug fixes MUST come with a regression test** that fails before the fix and passes after it,
  unless the behaviour cannot be reproduced without hardware or a service that cannot be scripted.
  In that case say so in the pull request and describe how you verified the fix by hand.
* Tests are part of the change, not a follow-up: a pull request whose checklist says "tests
  pending" is not ready for review.

### Unit tests

```bash
make test                              # everything except TestAcc*
go test {{PACKAGES}} -v                 # the package set the coverage gate measures
go test {{PACKAGES}} -run '^Test' -v    # skip the acceptance tests explicitly
```

### Acceptance tests

They need a running {{PRODUCT}} server and `TF_ACC=1`. The repository ships a compose fixture that
starts the server and runs the suite:

```bash
make testacc-docker      # Docker: server + Go test runner (this is what CI runs)
```

Or point the suite at your own server by exporting the endpoint and credential variables the
provider documents:

```bash
TF_ACC=1 go test -v {{PACKAGES}} -run TestAcc
```

The variable names a provider supports are documented in [`README.md`](README.md) and in the
provider's configuration schema. Never commit credentials; export them for the run.

### Coverage

Merged (unit + acceptance) statement coverage is enforced. `make coverage-gate` compares a profile
against [`.github/coverage-baseline.txt`](.github/coverage-baseline.txt), and the `Coverage` check
fails a pull request that drops below the floor. The badge and the sentence in `README.md` are
generated from that same file, so the published number and the enforced floor cannot drift apart.

```bash
make coverage            # unit profile + per-function coverage listing
make testacc-docker      # writes coverage-acceptance.out
make coverage-merge      # merge both into coverage-union.out
make coverage-gate       # fail when below the floor
```

To raise the floor: update the measured and floor values in `.github/coverage-baseline.txt` and run
`make coverage-readme`. Do that in the same pull request that adds the tests.

## Submitting changes

### Before submitting

1. `make fmt vet lint` and `make test` pass.
2. Acceptance tests pass for a new or changed resource (`make testacc-docker`).
3. `make generate` produces no `docs/` diff.
4. `make coverage-merge && make coverage-gate` passes, and the coverage floor in
   `.github/coverage-baseline.txt` is raised if the change improved it.
5. `make scaffold-check` passes, or the deviation is recorded with `--allow <path>:<reason>`.
6. The change is described in `CHANGELOG.md` under `Unreleased`.

### Pull request process

1. One feature or fix per pull request.
2. Use a descriptive title referencing the issue (for example
   `feat: add {{PROVIDER}}_group resource (#50)`).
3. Link related issues with `Fixes #123`.
4. Fill in the pull request template — it mirrors the review checklist below.

### Code review

Every change to `main` goes through a pull request. The ruleset is expected to require the
`ci / Lint & Security` and `ci / Test` checks to pass, forbid force-pushes and branch deletion,
dismiss stale reviews on new pushes and require review threads to be resolved;
[`GOVERNANCE.md`](GOVERNANCE.md) records the settings actually enabled. Reviewers check:

| Area | What has to be true |
|---|---|
| Correctness | The change does what the issue asks, including the error paths; no silently swallowed diagnostics |
| Tests | The testing policy above is met, and the tests fail when the fix is reverted |
| Schema and state | No renamed or removed type/attribute; new attributes are optional or computed, sensitive fields marked, `RequiresReplace()` where an in-place update is impossible; import still works |
| Docs and examples | Schema descriptions present, example added under `examples/`, `docs/` regenerated |
| Security | No credential in code, logs or fixtures; credentials `Sensitive`; input validation for anything user-supplied; no new network egress beyond the configured endpoint |
| Compatibility | The supported {{PRODUCT}} version behaviour is cited; capability gaps are reported rather than silently ignored |

A reviewer requests changes or approves in the pull request. The repository currently has a single
maintainer, so a pull request authored by the maintainer is merged by its author after CI is green —
the ruleset deliberately does not require an approval nobody can give. Adding a second reviewer
means enabling the approval requirement and `CODEOWNERS` in the same pull request that adds them to
[`GOVERNANCE.md`](GOVERNANCE.md).

## Good first issues

Issues labelled `good first issue` are scoped so that a first-time contributor can finish them
without deep provider knowledge: they name the file to change, the expected behaviour and the test
to extend. If the list is empty, ask in a new issue or pick a documentation or example improvement —
both are genuinely useful here.
